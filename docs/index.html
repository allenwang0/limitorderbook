Primer

A limit order book matches buyers and sellers by price, then by arrival#

Price, then time

A limit order names a side, a price and a quantity, and rests in the book until something trades against it. Bids are sorted highest first, asks lowest first, and orders at one price queue by arrival. An incoming order that crosses trades against the best price first, then the oldest order at that price, and every fill prints at the resting order's price.

In the committed replay of examples/demo_flow.txt, orders #120 and #121 both bid 9999 ticks, in that order. A sell of 17 at 9997 then arrives:

line 172  ADD 120 B 9999 15
  → accepted 15
line 175  ADD 121 B 9999 29
  → accepted 29
line 178  ADD 124 S 9997 17 IOC
  → accepted 17
  → fill 15 @ 9999 vs #120
  → fill 2 @ 9999 vs #121

#120 fills first (15) because it arrived first; #121 gets the remaining 2. Both fills print at 9999, the resting price, not the seller's 9997. The order is IOC (immediate or cancel), so any unfilled remainder would be cancelled; here 0 remain.

Result

FlatBook processes 1.86× as many messages per second#

The gap is not a product of run-to-run noise: the slowest FlatBook repetition still processed 1.72× as many messages as the fastest MapBook repetition.

For a price inside the window, FlatBook reaches its level with one array index, and its order nodes sit contiguously in one vector. MapBook walks a red-black tree — O(log n) pointer hops — and allocates a list node per resting order. The measured gap is consistent with that difference; this benchmark does not isolate which part contributes most.

Resolution

Single operations are too fast for the clock to separate#

Medians read 0 or one tick, so per-operation timing cannot separate the two books. Only the tail rises clearly above resolution: the largest p99.9 is MapBook market at 292 ns. Across the 10 runs, one series' p99.9 moved by up to 12.3×, so the tail is shown but not compared.

Mechanism

Orders live in one pooled array, linked by index#

Design decisions in FlatBook

Level array for 4,096 ticks
Instead of a std::map of levels: one index per lookup inside the window, at the cost of a range fixed up front.
Order nodes in one vector, uint32 links
Instead of a std::list node per order: nodes are reused through a free list, and links are half the size of pointers.
Open-addressing id index, Fibonacci hash
Instead of std::unordered_map: sequential ids spread across slots; the table doubles at load factor 0.5.
std::map for prices outside the window
Instead of rejecting or re-centring: correct at every price, slower outside the window.

Complexity

Cancels are constant-time on average, with three exceptions#

FlatBook's cancel is designed for average O(1): find the node in the id index, unlink it from its level's queue, and update the level total.[E9] Three cases cost more:

  1. Emptying the best level triggers a linear scan of up to 4,096 ticks for the next occupied level.
  2. Prices outside the window live in std::map, so their levels cost O(log n).
  3. The id index keeps its load factor at or below 0.5 and doubles when it would exceed it; the growth step is O(n).

Limitations

Results cover one core, one CPU and one synthetic workload#

  • One core, one CPU. All numbers are single-threaded on an Apple M5 Pro; other CPUs and compilers may give a different ratio.
  • Shared machine. Load average 5.77 / 8.20 / 6.84 at the start of the run. Whiskers show spread within this session only; absolute rates move between sessions more than the ratio does.
  • One synthetic flow. No sweep over book depth, price spread or window size, so where FlatBook's advantage ends is not measured.
  • Window tuned to the flow. Ticks 7,952–12,047 are centred on the synthetic prices; a flow that drifts out of the window falls back to std::map.
  • No allocation measurement. The benchmark does not count heap allocations, so this report makes no claim about them.
  • Unstable tail. p99.9 moved by up to 12.3× across runs; tails are shown, not compared.
  • Matching core only. No networking, market-data feed or multiple instruments.

Reproduce

Reproduce it in five commands#

Commands run from a clone of allenwang0/limitorderbook.

  1. Build in Release and run all tests (CMake 3.25+, Ninja, a C++17 compiler; downloads GoogleTest and Google Benchmark). Expect “100% tests passed”.

    cmake --workflow --preset default

  2. Run the benchmark (10 repetitions, about 17 s of timed work here), the replay, and rebuild this page, the card and the README table from the results.

    scripts/run_bench.sh

  3. Check the differential test line: “differential: 20 seeds x 100000 ops = 2000000 ops, 0 mismatches”.

    ./build/lob_differential_test

  4. Sanitizer build (Debug, ASan + UBSan); the differential test is much slower here.

    cmake --workflow --preset asan

  5. Check that every number on this page matches results/bench.json.

    python3 -m unittest discover -s tests -p 'test_*.py'
